# Kitlist

A packing checklist for trips. Make a trip, add the things you need, tick them
off as they go in the bag, and see at a glance what is still left.

No account, no server, no permissions, no network: everything lives on the
device.

**This is a deliberately small sample app.** It exists to show a complete,
working VibeView setup for an Expo project: cloud builds, device verification
by a coding agent, signing, and store submission. Read the story of how it was
built and shipped, with every command and output, in
[An AI agent shipped an Expo app to TestFlight in 43 minutes](https://vibeview.io/guides/ai-agent-shipped-expo-app-to-testflight/).
Copy the `vibeview.json` and the two config plugins into your own project; do
not expect much from the app itself.

Kitlist was built, verified on live iOS and Android devices, signed and
submitted to TestFlight and Google Play by a coding agent, using only the
[VibeView](https://vibeview.io) CLI for everything native. No Xcode or Android
Studio was involved at any point — Metro ran on the laptop, every native build
ran in VibeView's cloud, and every tap of the verification flow ran on a
VibeView cloud device.

## The app

- **Trips** — one row per trip with its start date, number of nights, a
  `packed / total` count and a thin progress bar (accent while packing, green
  once everything is in). `+` opens the new-trip sheet.
- **Trip** — `N left to pack` at the top (`All packed` when done), items
  grouped by category (Documents, Clothes, Toiletries, Tech, Other). Tap a row
  to toggle it; ticked rows get a green box and struck-through text and stay
  exactly where they are. Quantities above 1 show as `×4`. `+` opens the
  add-item sheet.
- **Sheet** — one bottom sheet used for both forms: item name, quantity and
  category chips with an `Add to <trip>` button, or trip name, start date and
  nights with `Create trip`.

Three example trips are seeded the first time the app starts; after that
every change is persisted with AsyncStorage.

Stack: Expo SDK 57 (managed workflow), TypeScript, Expo Router, AsyncStorage,
system fonts. The generated `ios/` and `android/` directories are not checked
in — `expo prebuild` recreates them for every build.

## Running it

```bash
npm install
npx expo start            # Metro
npm run typecheck         # tsc --noEmit
```

To run it on a phone you need a debug build. This project never produced one
locally; see below for how the cloud builds work. The app icon, adaptive icon
and splash image are generated by `python3 scripts/make-icons.py` (Pillow).

## `vibeview.json`

Everything the VibeView CLI needs is in `vibeview.json`:

| Key | What it does |
|---|---|
| `defaultPlatform` | Platform `vibeview build` / `vibeview dev` use when `--platform` is omitted. |
| `metroCommand`, `metroPort` | How `vibeview dev` starts Metro when nothing is listening on the port. |
| `platforms.<p>.appId` | The VibeView app record. Written by the CLI after the first successful cloud build — you never type it. |
| `platforms.<p>.build.command` / `.artifact` | The debug (simulator / emulator) build. Each command installs dependencies, runs `expo prebuild` for the platform, then drives `xcodebuild` (simulator SDK, no code signing) or `gradle assembleDebug`. `vibeview build --cloud --platform all` runs both in the cloud and registers the results as builds you can start a session on. |
| `platforms.<p>.build.productionCommand` / `.productionArtifact` | The signed release build used by `vibeview build --cloud --production`: an `xcodebuild archive` + `-exportArchive` producing an `.ipa`, or `gradle bundleRelease` producing an `.aab`. |
| `platforms.<p>.build.autoIncrement` | VibeView keeps a per-app build-number counter and passes the next value as `VIBEVIEW_BUILD_NUMBER`; `app.config.js` maps it to `ios.buildNumber` and `android.versionCode`. |

Signing is wired up with two small Expo config plugins in `plugins/`, because
a managed project has no native project files to edit:

- `withVibeViewSigning.js` appends a guarded `signingConfigs.release` block to
  the generated `android/app/build.gradle`, reading the four `VIBEVIEW_*`
  Gradle properties VibeView provides during a production build. Without them
  the block is inert, so debug builds are untouched.
- `withVibeViewIosSigning.js` sets manual code signing (team, provisioning
  profile) on the app target from `VIBEVIEW_DEVELOPMENT_TEAM` and
  `VIBEVIEW_PROVISIONING_PROFILE` at prebuild time. Doing it on the target —
  rather than on the `xcodebuild` command line, which would apply to every
  CocoaPods target too — is what the VibeView signing docs recommend for
  CocoaPods projects. The archive command only passes `CODE_SIGN_IDENTITY`
  and the export step uses the options plist VibeView writes.

The signing credentials themselves were generated by VibeView
(`vibeview credentials generate`) and are scoped to this app; nothing secret
is in the repository.

## Verifying it on a device yourself

You need the `vibeview` CLI installed and logged in (`npm i -g vibeview`,
`vibeview login`).

```bash
# 1. Build both debug apps in the cloud (only needed after native changes).
vibeview build --cloud --platform all

# 2. Start Metro, then a detached session on the platform you want.
npx expo start &
vibeview dev --detach --json --platform ios      # or android
# → {"event":"session_ready","session_id":"…","url":"https://vibeview.io/sandbox/…"}

# 3. Drive it. Every control has a testID and `find` resolves them on both platforms.
S=<session_id>
vibeview ui-tree --session $S                     # refs like @e3 come from here
vibeview find "trip.row.lisbon" --session $S      # → @e3 "Lisbon, long weekend, … 6 / 11"
vibeview tap @e3 --session $S                     # trip.left reads "5 left to pack"
vibeview find "item.row.swim-shorts" --session $S
vibeview tap @<ref> --session $S                  # "4 left to pack"; tap again → "5 left to pack"
vibeview find "item.add" --session $S
vibeview tap @<ref> --session $S                  # sheet opens with sheet.name focused
vibeview type "Sunscreen lotion" --session $S
vibeview find "sheet.cat.Toiletries" --session $S && vibeview tap @<ref> --session $S
vibeview find "sheet.save" --session $S && vibeview tap @<ref> --session $S
                                                  # new row under TOILETRIES, "6 left to pack"
vibeview press home --session $S
vibeview open-url "kitlist://" --session $S       # iOS: then `vibeview alert accept --button Open`
                                                  # app restarts on Trips; Lisbon shows 6 / 12
vibeview screenshot --out check.png --session $S

# 4. Always stop the session — it bills minutes while it runs.
vibeview dev-stop
```

`find "<testID>"` resolves on Android as well as iOS: a React Native `testID`
reaches the Android tree as the view's resource id, and VibeView matches it
the same way it matches the iOS accessibility identifier.

Accessibility ids: `trips.add`, `trip.row.<id>`, `trip.left`, `item.row.<id>`,
`item.add`, `sheet.name`, `sheet.qty`, `sheet.date`, `sheet.nights`,
`sheet.cat.<Category>`, `sheet.save`. Seed trip ids are `lisbon`, `tatras`,
`berlin`; item ids are the kebab-cased name (`swim-shorts`, `eu-plug-adapter`).

## Shipping

```bash
vibeview submit --check --platform ios --bundle-id io.vibeview.kitlist
vibeview submit --check --platform android --package io.vibeview.kitlist
vibeview build --cloud --production --platform all
vibeview submit --platform ios --latest                    # → TestFlight
vibeview submit --platform android --latest --track internal
```

Version 1.0.0 (build 1) of this app went to TestFlight and the Play internal
track this way.
